# 0C-VMC 自描述日志转换可行性分析

> 分析对象：`samples/0c_vmc/log_151_data_2026_09_18__09_54_15.bin`
>
> 分析日期：2026-09-22
>
> 结论：可以从日志内嵌表头生成原始量 JSON，并转换成 PAT 可直接读取的固定帧文件；当前 PAT 不能用一份现有 JSON 直接读取原始混合日志。

## 1. 样本核验结果

本次按字节顺序遍历了完整文件，没有通过搜索帧头跳过数据。核验结果如下：

| 项目 | 结果 |
| --- | ---: |
| 文件大小 | 28,786,145 字节 |
| 全局头 | `0x00000000` 至 `0x00000053`，84 字节 |
| 消息描述表 | `0x00000054` 至 `0x00002468` |
| 描述项 | 55 个消息 ID、33 个主题名 |
| 数据区 | 从 `0x00002469` 开始 |
| 完整数据帧 | 775,975 帧 |
| 实际出现的普通消息 ID | 39 个 |
| 特殊记录 | `0x0100` 文本 10 条、`0x0000` 元数据 1 条 |
| 有效数据结束位置 | `0x01B73808` |
| 文件尾填充 | 1,497 字节 `0xFF` |

描述表计算出的负载长度与全部普通数据帧的长度字节一致，数据区可以从头连续走到尾部填充，中途没有错位或未知消息 ID。这足以证明“按日志表头自动拆帧和生成字段清单”在该样本上可行。

数据区中较常见的消息包括：

| 消息 ID | 主题 | 帧数 | 表头字段数/用途 |
| --- | --- | ---: | --- |
| `0x00EA` | `ah_fmu` | 83,181 | 飞控健康状态 |
| `0x0009` | `td_link` | 83,181 | 链路健康状态 |
| `0x0008` | `starneto3070` | 41,591 | 设备健康状态 |
| `0x0108` | `starneto3070` | 41,472 | 45 字段惯导数据 |
| `0x0019` | `insaoaf` | 20,796 | 设备健康状态 |
| `0x0119` | `insaoaf` | 20,428 | 34 字段组合导航数据 |

## 2. 已确认的二进制结构

### 2.1 描述项

```text
A5 | 未确认字节 | message_id(u16, little) | topic[16]
   | format_length(u16, big) | "field@type,field@type,..."
```

- `topic` 是 16 字节、以 `0x00` 补齐的 ASCII 名称。
- `format_length` 是大端长度。
- 字段字符串只包含字段名和存储类型，没有单位、倍率、偏移、枚举和说明。
- 描述项第 2 字节表现为校验或控制值，但当前样本不足以确认算法。

### 2.2 数据帧

```text
5A | 未确认字节 | message_id(u16, little) | timestamp(u64, big)
   | payload_length(u8) | payload[payload_length]
```

- 消息 ID 使用小端；时间戳和负载中的多字节数值使用大端，属于混合端序。
- `payload_length` 与对应描述项计算出的长度在全部 775,964 个普通帧中一致。
- `0x0100` 是长度受控的 ASCII 信息，包含软件版本、编译时间和 `LOG_TIME`。
- 原始时间戳单调，但表头没有给出计时单位或与 UTC 的换算规则，暂时只能保留原始计数值。

### 2.3 类型映射

| 日志类型 | 实际占用 | 可映射的 PAT 类型 | 结论 |
| --- | ---: | --- | --- |
| `u8` / `i8` | 1 | `uint8` / `int8` | 可直接映射 |
| `u16` / `i16` | 2 | `uint16` / `int16` | 可直接映射 |
| `u32` / `i32` | 4 | `uint32` / `int32` | 可直接映射 |
| `r16` | 4 | `float32` | 样本帧长及数值均证明其存储为 4 字节 IEEE 754，不是 2 字节半精度 |
| `r32` | 4 | `float32` | 可直接映射 |
| `r64` | 8 | `float64` | 格式可映射，本样本描述表未使用 |
| `u64` | 8 | 暂无单字段类型 | 当前 PAT 不支持 `uint64`，可先拆成高/低两个 `uint32`，或后续补齐类型 |

字段按大端解码后得到合理值。例如 `yc1723.quality` 为 `0.2`、`scale_rpm` 为 `1.0`，首个 `ah_nav.abz` 为约 `-9.75662`。

## 3. 为什么原文件目前不能直接打开

PAT 当前 JSON 表达一类固定帧：一个固定帧头、一个固定总长度和一组固定偏移字段。该日志在同一个文件中交错保存 39 种实际出现的消息 ID，各消息负载长度和字段集合不同。现有模型还不能表达以下规则：

1. 从偏移 2 的消息 ID 选择不同模板；
2. 根据偏移 12 的长度字节决定帧长；
3. 在一个会话内维护多种采样频率和各自时间戳；
4. 把帧内 `u64` 时间戳直接用作曲线横轴；
5. 校验描述项及数据帧中的未确认字节。

因此，给原始文件生成一份普通 PAT JSON 会在第一处不同帧长的位置错位。把所有字段拼成一条超宽固定记录还需要时间对齐、缺失值和插值规则，会改变原始数据含义，不作为首选方案。

## 4. 现有 PAT 无需改造的兼容转换方案

若保持当前 schema 2 和解析器完全不变，可按消息 ID 解复用，每个 ID 生成一对文件：

```text
<topic>_0x<id>.json
<topic>_0x<id>.bin
```

输出 `.bin` 使用稳定的 PAT 固定帧：

```text
A5 5A | message_id(u16, little) | original_timestamp(u64, big) | original_payload
```

对应 JSON 使用 `schema_version: 2`、大端字段和 4 字节固定帧头。例如 `ah_nav/0x00E7` 的原负载为 139 字节，转换记录为 151 字节：

```json
{
  "schema_version": 2,
  "template_id": "vmc_ah_nav_0x00e7_v1",
  "record_size": 151,
  "endianness": "big",
  "framing": {
    "kind": "fixed_header",
    "header_hex": "A55AE700",
    "frame_length": 151
  },
  "signals": [
    {
      "name": "log_timestamp_high",
      "byte_offset": 4,
      "value_type": "uint32",
      "group": "帧信息"
    },
    {
      "name": "cur_pos_x",
      "byte_offset": 12,
      "value_type": "float32",
      "group": "ah_nav"
    }
  ]
}
```

转换器需要执行以下规范化：

- 把描述表中的字段偏移整体加 12；
- 将 `r16` 和 `r32` 都映射为 `float32`；
- 将 `u64` 暂时拆成 `_high`、`_low` 两个 `uint32`；
- 对同一消息内的重名字段追加序号。样本中的 `ah_nav.tas_est_dxy` 出现两次；
- 将原始时间戳保留为高/低 32 位信号，直到确认单位并实现时间戳横轴；
- 输出扩展名使用 `.bin`。PAT 会把 `.log` 当作十六进制文本，不能给二进制转换结果使用 `.log` 后缀；
- 不写入未经确认的 `scale`、`bias` 和 `unit`，原始值默认倍率为 1。

该方案只重排和筛选记录，不修改负载字节。每个输出文件可由当前 PAT 的“打开格式”和“打开数据”流程加载。不同消息 ID 仍需分别打开，不能在当前单会话中跨 ID 合并曲线，因此作为兼容和验证出口保留；统一分析采用第 8 节的固定信封记录和流路由方案。

## 5. PAT 原生导入的建议方案

若希望用户直接选择原始 VMC 文件并同时查看全部主题，应在 C++/Qt 方案中增加 `SelfDescribingLogImporter`，而不是长期要求用户运行外部脚本。

建议流程为：

1. 流式读取全局头和描述表，建立 `message_id → FormatDefinition`；
2. 逐帧校验同步字、消息 ID、长度以及可选的校验算法；
3. 为每个消息 ID 建立独立时间序列，以原始时间戳配对本消息字段；
4. 在导入对话框中列出主题、消息 ID、字段数和帧数，允许选择导入范围；
5. 提供“直接导入当前会话”和“导出 PAT JSON + BIN”两个动作；
6. 保存一份清单，记录源文件摘要、描述表、未识别类型、重名修正和丢弃帧原因。

解析为单次线性扫描，时间复杂度为 `O(文件大小)`；描述表只有 55 项，不构成性能压力。27.5 MiB 样本无需整文件驻留内存，转换器可按块读取并按消息 ID 追加写入。若同时打开全部主题，主要内存成本来自 PAT 当前离线曲线全量驻留，应复用现有抽稀显示，并在后续加入按主题懒加载或磁盘索引。

## 6. 原型验证

本次使用独立临时原型把 `ah_nav/0x00E7` 转换为 16,636 条、每条 151 字节的固定帧，共 2,512,036 字节；自动生成 JSON 含 51 个信号，其中包括 49 个表头字段和时间戳高/低位。

随后直接调用当前 `FormatDefinition` 和 `DataSession` 加载该 JSON 与转换文件，得到：

```text
signals=51 samples=16636 first_abz=-9.75662
```

这证明“按 ID 拆分 → 生成 JSON → 转换 BIN → 当前 PAT 读取”的链路可行。该原型只用于验证，尚未作为产品功能提交。

## 7. 实施前仍需确认

以下信息不能从这一个日志样本可靠推出：

1. 描述项和数据帧第 2 字节的算法及覆盖范围；
2. 64 位时间戳的单位、起点、回绕规则及其与 `LOG_TIME` 的关系；
3. 各字段的工程单位、比例、物理偏移、枚举和有效范围；
4. `r16` 名称为何对应 4 字节浮点，以及其他固件版本是否保持相同定义；
5. 文件全局头各字段、结束条件，以及异常断电日志的恢复规则。

即使以上信息暂未补齐，也可以先实现原始量导入和转换。界面必须将这些字段标为“表头未提供”，避免把默认倍率 1 和采样序号误解为已确认的工程单位与真实时间。

## 8. 多文件统一 BIN 与统一 JSON

进一步检查消息调度后，确认 `0x00EA` 可用于观察主周期，其他消息大致按 1、2、4、5、10、16、25、30、50 倍周期调度；但全文件有 312 种周期内序列，存在启动记录、条件缺帧和单周期同 ID 多帧。正式转换不能依赖固定顺序或按主周期只保留一个值。

先前约 4.94 GiB 的估算来自错误的“每个源帧都为全部 427 个字段追加点”实现，并不是日志重构的必然成本。正确方案把每个源帧包装成一条固定信封记录，通过 `stream_id` 只解码匹配流；该样本实际约 800 万有效点，`QPointF` 原始点载荷约 122 MiB。当前 139 字节最大负载加 40 字节信封头和 CRC 后形成 179 字节固定记录，统一 BIN 约 132.46 MiB。

完整固定记录布局、JSON 路由字段、合并规则、模块划分和验收标准见 [PAT 统一混合日志格式设计](PAT统一混合日志格式设计.md)。逐消息 ID 的固定帧 JSON/BIN 继续作为兼容导出。
