# 设计日志

记录设计思路、决策与阶段目标，便于协作与追溯。

## 记录原则
- 尽量小步快记：每次关键决策、里程碑、方案取舍都要补充。
- 明确版本/日期，指出影响范围（核心解析、GUI、构建、测试等）。

## 2026-01-06 初始规划
- 背景：飞参解析，格式用 JSON 描述，数据为 bin/dat 时序数值，需折线图展示，体积尽量小，后续希望把核心迁移到 Web 端。
- 架构取向：核心解析库与 GUI 解耦；核心仅依赖标准库 + RapidJSON + fmt + spdlog，保留 Emscripten 兼容性。
- GUI 方案：预留两种构建选项——Qt（全功能）与 ImGui+ImPlot（轻量）。默认优先实现轻量方案以控制体积。
- 数据处理：按时间轴流式解析，建立轻量索引，支持极值统计、对齐、多格式并行解析；后处理可插拔。
- 里程碑：
  - M1 CLI 核心：格式加载/校验、二进制解析、极值统计、CSV 导出、单元测试。
  - M2 GUI 轻量版：数据加载、曲线绘制、缩放/框选、导出。
  - M3 工程化：项目文件、批量解析、多格式并行、异常检测可视化。
  - M4 Web 迁移预研：Emscripten 编译核心，稳定 C API/FFI。
  - M5 发布：打包脚本、CI 产物。
- 待决事项：
  - JSON 格式描述具体字段：类型/字节序/单位/尺度/时间戳规则/校验（CRC/校验和）。
  - GUI 方案最终选型（Qt vs ImGui），是否需要脚本扩展（Python/Lua）。
  - 是否需要压缩日志支持（zlib）与多线程解析/绘图并发策略。

## 2026-09-22 0C-VMC 自描述日志分析（路线文档 2.8.0）
- 样本：检查 `samples/0c_vmc/log_151_data_2026_09_18__09_54_15.bin`，确认文件含 55 个消息描述项，数据区交错保存多种消息 ID 和帧长；完整遍历得到 775,975 帧且长度全部与描述表一致。
- 结论：现有单一固定帧 JSON 不能直接读取原文件；按消息 ID 解复用后可自动生成 PAT JSON 和固定帧 BIN。`r16` 在该格式中实际为 4 字节浮点，消息 ID 为小端，时间戳及负载为大端。
- 验证：临时原型转换 `ah_nav/0x00E7` 的 16,636 帧，当前 PAT 核心成功加载 51 个信号并复核 `abz=-9.75662`。正式实现列为 TC-14，沿用 C++20、Qt 6 和 `pat_core`，不增加 Python 运行时。
- 待确认：帧内未确认字节的校验算法、时间戳单位、工程单位/倍率以及异常断电日志规则。详细证据见 [0C-VMC 日志转换可行性分析](0C-VMC日志转换可行性.md)。

## 2026-09-22 统一混合日志格式（路线文档 3.0.0，后由 3.1.0 修正）
- 调度分析：`0x00EA` 可观察主周期，其他消息呈 2/4/5/10/16/25/30/50 倍分频；但实际有 312 种周期内序列、启动记录、条件缺帧和同周期重复 ID，不能按固定顺序或每周期单值转换。
- 方案：统一文件采用分块、多流、带索引的 `PAT Mixed Binary v1`，配套 `schema_version: 3` JSON；保存原始时间戳、来源序号、状态和负载，使用结构 SHA-256 绑定布局，按块 CRC 校验。
- 读取：新增 `MixedDataSession`，只加载用户实际使用的流和字段，每条信号保留自身时间戳。427 字段主周期宽表会占约 542 MiB 基础点内存且丢失重复帧，因此只保留为显式导出。
- 多文件：先建立来源段；时间基准未确认时不按文件名强行拼时轴，结构冲突建立新流版本，重复和损坏记录保留可追溯状态。详细规范见 [PAT 统一混合日志格式设计](PAT统一混合日志格式设计.md)。

## 2026-09-22 固定记录路由修正（路线文档 3.1.0）
- 修正：4.94 GiB 是把每条源记录与全部 427 个字段做笛卡尔展开后的错误实现成本，并非统一 BIN 的必然成本。按流 ID 路由后只产生 8,006,657 个有效点，`QPointF` 原始点载荷约 122.17 MiB。
- 格式：每个源帧重构为 `PATM` 固定记录，40 字节头保存流 ID、来源段、原始时间戳、源序号、源帧头、状态和记录 CRC，后接本批最大负载区；当前样本记录长 179 字节，统一 BIN 约 132.46 MiB。
- JSON：schema v3 保留现有 `record_size`、`endianness`、`framing`，增加 `dispatch`、`timestamp`、`payload_offset` 和 `streams`。解析器只解码匹配流，不给其他信号补零或无效点。
- 实施：schema 1/2 及现有固定帧流程保持不变；新增独立 `RoutedRecordParser` 和 `MixedDataSession`，详细规范见 [PAT 统一混合日志格式设计](PAT统一混合日志格式设计.md)。

## 2026-09-22 大文件与低内存约束（路线文档 3.2.0）
- 风险：按流路由消除了 4.94 GiB 的笛卡尔展开，但全量有效点在 10/20 倍数据下仍约占 1.22/2.44 GiB 原始 `QPointF`；Qt 容器、图表和派生数据还会继续放大，不能全量驻留。
- 存储：179 字节固定信封在 20 倍数据下约 2.59 GiB，降为兼容导出。默认 BIN 按流紧凑分块，当前约 29–33 MiB，10 倍约 0.3 GiB，20 倍约 0.6 GiB，并在文件尾保存时间范围索引。
- 运行：打开时只读 JSON 和索引；按所选信号与可见时间范围解码。缓存默认 128 MiB、低内存模式 64 MiB，转换缓冲不超过 64 MiB，每条可见曲线仍限制约 4,000 个抽稀点。
- 验收：增加 10 倍和 20 倍合成数据，要求常驻内存受预算限制；离线空间轨迹改用块索引和分层概览，不复制全量历史。
