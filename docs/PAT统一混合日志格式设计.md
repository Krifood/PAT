# PAT 统一混合日志格式设计

> 文档版本：1.0.0
>
> 日期：2026-09-22
>
> 适用范围：把一个或多个 VMC 自描述日志稳定转换为一个 PAT 混合数据 BIN 和一个 JSON，并在 PAT 中按真实时间戳分析多频率信号。

## 1. 决策

可以生成“一个 BIN + 一个 JSON”，但 BIN 必须是带流标识、分块索引和时间戳的混合数据容器，JSON 必须升级为能描述多消息流的 `schema_version: 3`。不能用当前单帧 `FormatDefinition` 把所有消息机械铺成普通固定宽记录作为正式方案。

正式方案包含：

- 一个 `*.bin`：保存多个消息流的数据块、原始时间戳、来源段和校验结果；
- 一个 `*.json`：保存所有流及字段格式、时间基准、来源清单和结构指纹；
- 一个 `MixedLogReader`：按索引只加载当前使用的流和字段；
- 一个 `MixedDataSession`：每条信号保留自己的时间点，不要求不同流拥有相同采样数量；
- 一个 C++/Qt 转换入口：可导入一个文件，也可批量导入多个分段文件。

原有逐消息 ID 导出固定帧 JSON/BIN 的方案保留为兼容导出，适合当前 PAT 验证或交给其他固定帧工具，不作为统一分析的内部存储。

## 2. 当前日志格式和记录规律

### 2.1 文件结构

当前样本由全局头、描述表、数据帧和尾部填充组成：

```text
[84 字节全局头]
[55 个 A5 描述项]
[775,975 个 5A 数据/元数据帧]
[1,497 字节 FF 填充]
```

描述项：

```text
A5 | 未确认字节 | message_id(u16, little) | topic[16]
   | format_length(u16, big) | "field@type,field@type,..."
```

数据帧：

```text
5A | 未确认字节 | message_id(u16, little) | timestamp(u64, big)
   | payload_length(u8) | payload[payload_length]
```

负载字段使用大端；`r16` 和 `r32` 均实际占 4 字节并按 IEEE 754 单精度解释。消息 ID、名称和负载长度可以作为稳定路由依据。帧内未确认字节、时间戳单位、工程单位和倍率不能从当前样本单独确定。

### 2.2 调度规律

`ah_fmu/0x00EA` 在样本中出现 83,181 次，可作为观察调度规律的主周期标记。相邻标记的原始时间戳差值中位数为 10,001,811，范围为 9,544,955 至 10,510,222；计时单位尚未确认。

| 周期关系 | 代表消息 | 规律 |
| --- | --- | --- |
| 每个主周期 | `0x00EA ah_fmu`、`0x0009 td_link` | 83,181 次，严格每周期出现 |
| 每 2 周期 | `0x0008 starneto3070`、`0x00E1 ha_heli` | 相邻出现周期差固定为 2 |
| 每 4 周期 | `0x0019 insaoaf` | 相邻出现周期差固定为 4 |
| 每 5 周期 | `0x00E7 ah_nav`、`0x00ED ah_rate_ctrl` 等 | 多数控制、导航数据按 5 周期出现 |
| 每 10 周期 | `0x00EC/0x01EC ah_pos_ctrl`、`0x00F0 ah_att_ctrl` | 相邻出现周期差固定为 10 |
| 每 16 周期 | `0x0012 mcu` | 健康帧固定为 16 周期 |
| 每 25 周期 | `0x0013 xt126` | 固定为 25 周期 |
| 每 30 周期 | `0x010C tcuc31` | 固定为 30 周期 |
| 每 50 周期 | `0x0114 fv_3500` | 固定为 50 周期 |

该规律只适合性能估算和异常提示，不能作为拆帧规则：

- 主周期之前已有 9 个普通记录，使用 `0x00EA` 作为硬分隔会漏掉启动数据；
- 全文件出现 312 种不同的周期内消息序列；
- `0x0105` 在一个主周期内最多出现 4 次，`0x010A` 最多出现 3 次；
- `0x0108` 的周期间隔为 1 至 3，`0x0119` 为 3 至 5；
- `0x0105`、`0x0112`、`0x0205` 等数据帧会因设备状态出现缺帧或周期漂移；
- 固定频率消息的相位也有抖动，不能按字节位置或周期内序号识别消息。

因此转换器必须逐帧使用同步字、消息 ID、负载长度和描述表处理。时间戳用于排序和对齐，调度周期仅作为诊断信息。

## 3. 普通固定宽统一记录为什么不适合作为正式方案

实际出现的 39 个消息 ID 共包含 427 个字段，所有消息的一份原始负载合计 1,128 字节。

### 3.1 每个原始帧生成一条宽记录

若每条记录为所有字段保留 `float64` 位置，并加入时间戳和消息更新标志，单条约 3,506 字节。775,964 个普通帧会生成约 2.53 GiB 文件。当前 PAT 把每个字段的每个点展开为 `QPointF`，仅 427 条序列的点数据约 4.94 GiB，尚未计算容器、统计和图形副本。

每条事件只有一个消息有值，其余字段只能填 `NaN` 或旧值；前者产生大量空洞，后者会把“未更新”伪装为新采样。

### 3.2 每个主周期生成一条快照记录

83,181 个主周期按原类型打包约 96.62 MiB；全部转为 `float64` 约 278.12 MiB。文件大小可以接受，但当前 PAT 展开后的点数据仍约 541.97 MiB，并且还存在以下数据损失：

- 同一流在一个周期内多次出现时只能保留一条；
- 主周期之前的数据无法自然归属；
- 条件缺帧需要选择填零、`NaN` 或前值保持，每种方式都会改变部分分析语义；
- 低频信号被重复成主周期频率，统计数量和差分结果失真；
- 多文件时间戳重置时无法只靠记录序号正确拼接。

该格式可以作为用户明确选择采样周期和填充策略后的“宽表导出”，不能作为 PAT 的标准导入格式。

## 4. 统一 BIN 容器

统一容器暂定为 `PAT Mixed Binary v1`，文件仍可使用 `.bin`，通过 8 字节魔数区分普通固定帧文件。

### 4.1 文件头

所有容器控制字段统一使用小端，文件头固定 64 字节：

| 偏移 | 长度 | 字段 | 说明 |
| ---: | ---: | --- | --- |
| 0 | 8 | `magic` | ASCII `PATMBIN1` |
| 8 | 2 | `version` | 固定为 1 |
| 10 | 2 | `header_size` | 固定为 64 |
| 12 | 4 | `flags` | 首版为 0 |
| 16 | 32 | `layout_sha256` | JSON 结构字段的规范化 SHA-256 |
| 48 | 8 | `index_offset` | 文件尾索引起始位置 |
| 56 | 4 | `chunk_count` | 数据块数量 |
| 60 | 4 | `stream_count` | 流数量 |

`layout_sha256` 只覆盖流 ID、负载长度、字段偏移、类型和端序。用户补充单位、说明、倍率或界面分组时不改变结构指纹；修改偏移或类型后必须重新转换或显式迁移。

### 4.2 数据块

每个数据块只保存一个流、一个来源段，块头固定 48 字节：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `magic` | 4 字节 | ASCII `PCHK` |
| `header_size` | `u16` | 48 |
| `flags` | `u16` | 压缩、校验状态等；首版不压缩 |
| `stream_id` | `u32` | PAT 内部稳定流编号 |
| `source_segment_id` | `u32` | 来源文件或连续日志段编号 |
| `record_count` | `u32` | 块内记录数 |
| `payload_size` | `u32` | 本流固定负载长度 |
| `first_timestamp` | `u64` | 块内首时间戳 |
| `last_timestamp` | `u64` | 块内尾时间戳 |
| `data_size` | `u32` | 块数据字节数 |
| `crc32` | `u32` | 块数据 CRC-32 |

块内每条记录为：

```text
timestamp_raw(u64) | source_sequence(u64) | record_flags(u32) | payload[payload_size]
```

- `timestamp_raw` 原样保存设备时间戳；
- `source_sequence` 保存该来源文件中的原始帧序号，用于追溯和稳定排序；
- `record_flags` 记录原帧校验已验证、校验未知、重复、时间回退等状态；
- `payload` 保持源字节和源端序，不做浮点往返转换；
- 块建议限制为 65,536 条记录或 4 MiB 数据，控制转换和读取峰值内存。

文件尾保存块索引及索引 CRC。读取器可只读取所选流的块，不必扫描整个文件。写入使用临时文件和 `QSaveFile` 提交；转换中断不会覆盖已有结果。

## 5. 统一 JSON

`schema_version: 3` 引入 `container`、`timebase`、`streams` 和可选 `source_segments`。示意结构如下：

```json
{
  "schema_version": 3,
  "template_id": "vmc_mixed_20260918_v1",
  "container": {
    "kind": "pat_mixed_bin",
    "version": 1,
    "magic": "PATMBIN1",
    "layout_sha256": "..."
  },
  "timebase": {
    "source": "record_timestamp",
    "value_type": "uint64",
    "unit": "tick",
    "scale": null
  },
  "streams": [
    {
      "stream_id": 231,
      "source_message_id": "0x00E7",
      "name": "ah_nav",
      "payload_size": 139,
      "endianness": "big",
      "signals": [
        {
          "name": "cur_pos_x",
          "source_name": "cur_pos_x",
          "byte_offset": 0,
          "value_type": "float32",
          "source_type": "r32",
          "scale": 1.0
        }
      ]
    }
  ],
  "source_segments": []
}
```

规则如下：

- `stream_id` 由“来源格式 + 消息 ID + 结构签名”生成，不能只按主题名生成；
- 同一消息 ID 在不同文件中结构签名不同，则建立不同流版本，禁止静默套用旧格式；
- 信号名重复时追加 `_2`、`_3`，并用 `source_name` 保存原名；
- schema v3 补齐 `uint64` / `int64`，不再拆分 64 位字段；
- 未知时间单位写 `tick` 且 `scale` 为 `null`，界面显示原始计数，不标成秒；
- 表头没有提供的单位、倍率、偏移和说明保持空值，并显示“表头未提供”；
- `source_segments` 记录输入文件 SHA-256、文件大小、日志版本文本、起止时间戳、描述表结构签名和转换告警。

## 6. 多文件合并规则

批量转换不能按文件名或选择顺序直接拼接，必须建立来源段：

1. 每个输入文件先独立验证全局头、描述表、帧边界和尾部；
2. 以消息 ID 和结构签名匹配流；同 ID 不同结构创建新流版本；
3. 保留每条记录的来源段和原始序号；
4. 只有时间单位、起点和跨文件关系已确认时，才生成统一绝对时间；
5. 时间基准未确认时按来源段分别展示，段边界处断线，不把两段曲线直接相连；
6. 完全相同的 `(来源会话、消息 ID、时间戳、负载)` 可标为重复并按用户选项去重；同时间戳但负载不同的记录全部保留并报告冲突；
7. 某文件损坏时输出已验证块和错误位置，默认不猜测跨越未知字节；用户显式启用恢复扫描后，恢复记录必须带状态标志。

当设备文档确认时间戳单位和 `LOG_TIME` 关系后，可为每个来源段写入 `normalized_time = raw_timestamp × scale + offset`。在此之前不根据文件创建时间或文件名推算绝对时间。

## 7. PAT 读取和显示模型

现有 `DataSession` 会为 JSON 中每个字段一次性生成完整 `QPointF` 数组，不适合 427 个多频率字段。稳定实现增加独立的 `MixedDataSession`：

- 打开时只读取文件头、索引和 JSON，不展开全部点；
- 信号树立即显示全部流和字段；
- 用户勾选、搜索、统计或绑定二维/三维坐标时，按索引加载所需字段；
- 每条信号使用自己的时间戳数组，差值/和值先按既有时间对齐策略处理；
- 缓存按“流 + 字段 + 时间范围”管理，可设置内存上限并淘汰不可见数据；
- 统计值按块计算并缓存，读取大文件时提供可取消进度；
- 源文件、转换 BIN 和 JSON 的结构指纹不一致时拒绝解析并给出明确错误。

这种模型保留所有原始采样，不需要补零、前值保持或重复低频点，也能让不同消息流在一张时序图或空间图中组合。

## 8. 模块划分

| 模块 | 职责 |
| --- | --- |
| `VmcLogReader` | 流式读取描述表和原始帧，验证 ID、长度、尾部及时间单调性 |
| `MixedFormatDefinition` | 解析和验证 schema v3、多流、时间基准与结构指纹 |
| `PatMixedWriter` | 分块写入、CRC、索引、临时文件提交和来源清单 |
| `PatMixedReader` | 校验文件头/索引，按流和时间范围读取块 |
| `MixedDataSession` | 多频率时间序列、懒加载、缓存、统计和派生信号 |
| `MixedLogImportDialog` | 文件选择、扫描摘要、流选择、冲突提示、转换进度和结果入口 |

核心读写模块仅依赖 Qt Core，界面层依赖 Widgets。转换在工作线程运行，通过有界批次报告进度和错误；取消操作关闭临时文件并保留原始输入。

## 9. 实施顺序与验收

### 阶段 A：源格式读取

- 完成 `VmcLogReader` 和 55 项描述表解析；
- 完整样本必须得到 775,975 帧、39 个实际普通流和 1,497 字节尾填充；
- 覆盖截断描述项、未知类型、长度不符、时间回退、重复字段名及非 `FF` 尾部测试。

### 阶段 B：统一容器

- 完成 schema v3、分块写入、结构指纹、CRC 和索引读取；
- 逐流往返后，时间戳、来源序号和负载必须与输入逐字节一致；
- 转换取消、磁盘写满和目标文件已存在时不留下被误认为有效的结果。

### 阶段 C：PAT 集成

- 增加混合日志打开入口、流摘要和多频率 `MixedDataSession`；
- `ah_nav.abz` 首值应为约 `-9.75662`，各流样本数与扫描统计一致；
- 搜索、时序图、差/和、二维/三维图只触发所需字段加载；
- 27.5 MiB 样本打开阶段不展开全部 427 条序列，内存峰值和取消响应在目标机器验收。

### 阶段 D：多文件合并

- 验证相同结构连续段、时间戳重置段、重复文件和同 ID 结构冲突；
- 未确认时间基准时段间断线，确认换算后按标准时间排序；
- 输出来源清单可追溯每条记录所在源文件和原始序号。

## 10. 最终结论

通过规则把分散数据转成一个 BIN 并由一个 JSON 读取是可行的。稳定实现应采用多流容器和 schema v3，保留每条记录的流 ID、原始时间戳、来源及负载，并让 PAT 按需加载各流。基于主周期生成超宽快照只能作为显式导出功能，因为它会丢失同周期重复帧、扭曲低频信号并显著放大内存占用。
