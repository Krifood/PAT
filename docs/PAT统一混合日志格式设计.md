# PAT 统一混合日志格式设计

> 文档版本：3.0.0
>
> 日期：2026-09-22
>
> 适用范围：把一个或多个 VMC 自描述日志重构为一个紧凑、可索引的统一 BIN 和一份与现有 PAT 模板相近的 JSON，并在普通性能设备上分析大文件。

## 1. 修订结论

可以通过规则把分散数据重构成一个统一 BIN，再使用一份统一 JSON 解析。无需把每条记录展开为全部 427 个字段，也无需先按主周期形成超宽快照。

面向当前样本的固定信封记录可以工作，但最大负载补齐会把 27.5 MiB 源文件放大到约 132.46 MiB；数据增长 20 倍时约为 2.59 GiB，不适合作为低配置设备的默认格式。正式方案采用“按流分块紧凑存储 + 索引路由 + 有界缓存”：

- 一个数据块只包含一个流和一个来源段，块内负载长度固定，不按全局最大负载补齐；
- 每条记录保存时间戳、源序号、状态和原始负载，数据块保存流 ID、来源段、负载长度和 CRC；
- 文件尾索引可直接定位流和时间范围，打开文件时不扫描或解码全部数据；
- JSON 继续使用 `signals[].byte_offset/value_type/scale` 等现有字段，在外层增加 `storage`、`timestamp` 和 `streams`；
- 解析器只读取当前显示或计算需要的流、字段和时间窗口；
- 不属于当前流的字段不生成零值或 `NaN` 点。

这种设计保留全部原始帧及多频率采样，一份 BIN 和一份 JSON 即可打开分析。179 字节固定信封继续作为与普通固定记录工具交换的兼容导出，不作为大文件默认存储。

## 2. 当前日志格式与规律

### 2.1 源文件结构

```text
[84 字节全局头]
[55 个 A5 描述项]
[775,975 个 5A 数据/元数据帧]
[1,497 字节 FF 填充]
```

描述项：

```text
A5 | 未确认字节 | message_id(u16, little) | topic[16]
   | format_length(u16, big) | "field@type,field@type,..."
```

数据帧：

```text
5A | 未确认字节 | message_id(u16, little) | timestamp(u64, big)
   | payload_length(u8) | payload[payload_length]
```

已确认规则：

- 消息 ID 是小端；时间戳和负载多字节字段是大端；
- `r16` 和 `r32` 均实际占 4 字节并按 IEEE 754 单精度解释；
- 55 个描述 ID 中有 39 个普通 ID 实际出现；
- 39 个流共有 427 个字段，最大普通负载为 139 字节；
- 描述表计算长度与全部 775,964 个普通数据帧一致；
- 帧内第 2 字节、时间戳单位、工程单位和倍率尚未确认。

### 2.2 调度规律不能作为解析规则

`0x00EA ah_fmu` 可用于观察主周期，其他消息大致按 1、2、4、5、10、16、25、30、50 倍周期调度。但样本中存在：

- 主周期前 9 条普通启动记录；
- 312 种周期内消息序列；
- 一个主周期内 `0x0105` 最多 4 帧、`0x010A` 最多 3 帧；
- `0x0108`、`0x0119`、`0x0105`、`0x0112`、`0x0205` 等条件缺帧或周期漂移；
- 消息相位抖动。

所以转换必须逐帧依赖同步字、消息 ID、负载长度和描述表。主周期只用于频率统计和异常提示，不用于决定记录边界、字段位置或取舍数据。

## 3. 4 GiB 估算的来源与修正

4 GiB 估算来自不合适的实现：若把每个源事件作为一条记录，同时让当前 `DataSession` 对全部 427 个字段都追加一个 `QPointF`，会形成约 3.31 亿点，仅 `QPointF` 原始载荷约 4.94 GiB。这是“记录数 × 全部字段数”的笛卡尔展开，不是统一 BIN 必须付出的成本。

正确路由后，只为当前消息流的字段追加点。该样本的有效点数为：

```text
Σ(流帧数 × 该流字段数) = 8,006,657 点
```

按每个 `QPointF` 16 字节计算，原始点载荷约 122.17 MiB。若只加载用户勾选的字段，内存还会进一步下降。容器、统计、图形和缓存仍有额外开销，但不再接近 4 GiB。

发生笛卡尔展开时，4.94 GiB 只是点坐标下限。`QVector` 预留容量、Qt Charts 内部点副本、显示变换、统计和空间轨迹会继续增加占用，实际进程可能达到数倍于源文件的内存。普通设备会出现长时间加载、内存压缩和交换、界面失去响应、缩放或切换主题卡顿，最终可能分配失败或被系统终止；差/和、空间轨迹和导出还会重复扫描数亿个无效点。

## 4. 重构后的 BIN

### 4.1 固定信封兼容格式

每条输出记录使用统一大端控制字段，固定头 40 字节：

| 偏移 | 长度 | 字段 | 说明 |
| ---: | ---: | --- | --- |
| 0 | 4 | `magic` | ASCII `PATM`，即 `50 41 54 4D` |
| 4 | 4 | `stream_id` | 由消息 ID 与结构签名生成的内部流 ID |
| 8 | 4 | `source_segment_id` | 输入文件或连续日志段编号 |
| 12 | 8 | `timestamp_raw` | 原始 64 位时间戳 |
| 20 | 8 | `source_sequence` | 在来源文件中的原始帧序号 |
| 28 | 4 | `source_prefix` | 原始 `5A`、未确认字节及小端消息 ID，逐字节保留 |
| 32 | 2 | `payload_length` | 实际负载长度 |
| 34 | 2 | `record_flags` | 校验未知、已验证、重复、时间回退、恢复扫描等状态 |
| 36 | 4 | `record_crc32` | 对偏移 4–35 与完整负载区计算的 CRC-32 |
| 40 | N | `payload_area` | 原始负载，剩余字节补零 |

`N` 是本次转换所有输入流的最大负载长度。当前样本 `N=139`，因此固定 `record_size=179`，完整 775,975 帧约 132.46 MiB。该放大来自固定负载区补齐和记录校验，用于换取简单、稳定、可随机定位的记录；负载内容本身不做浮点往返转换。

特殊文本和元数据帧可作为独立流保留；首版也可以写入 JSON 的来源元数据并不进入数值信号树。文件尾 `FF` 填充不转入数据记录，但在来源清单中保存字节数。

### 4.2 流 ID

内部 `stream_id` 不能只等于主题名或源消息 ID。稳定键为：

```text
来源格式标识 + 源消息 ID + 字段名称/类型顺序 + 负载长度
```

转换器对该结构计算 SHA-256，并分配稳定的 32 位流 ID。同一个消息 ID 在不同文件里结构发生变化时生成新流，禁止静默使用旧字段偏移。

### 4.3 多文件记录顺序

- 单文件转换保持源记录顺序；
- 多文件先建立 `source_segment_id`，再决定是否能按时间合并；
- 时间单位和跨文件起点未确认时保持来源段顺序，段边界不连接曲线；
- 时间基准确认后，可按规范化时间稳定排序；相同时间使用来源段和源序号保证确定顺序；
- 完全相同的来源会话、消息 ID、时间戳和负载可以标为重复，默认保留并报告，用户可选择去重。

### 4.4 默认紧凑分块格式

正式统一 BIN 以流为单位分块。文件头保存版本、JSON 结构指纹和文件尾索引位置；每个块只保存一个 `stream_id`、一个 `source_segment_id` 和相同长度的负载。

块内记录为：

```text
timestamp_raw(u64) | source_sequence_delta(u32)
| record_flags(u16) | source_control(u8) | payload[payload_length]
```

每条普通记录的固定开销为 15 字节；数据块另有首尾时间、记录数、负载长度和 CRC-32。当前样本普通负载合计约 17.82 MiB，按 15 字节记录开销估算，统一 BIN 约 29 MiB，加索引和块头后仍与源文件同一量级。10 倍约 0.3 GiB，20 倍约 0.6 GiB。

数据块目标大小为 1–4 MiB，转换器所有流的写缓冲总量限制为 32 MiB；达到总量上限时优先刷出最久未使用的块。文件尾索引记录块偏移、流 ID、来源段、时间范围、记录数和 CRC，使读取器可以直接跳到所选时间窗口。

固定信封与紧凑分块共用同一套流定义。兼容导出强调记录结构简单；默认分块格式强调大文件空间、随机访问和有界内存。

## 5. 与现有 PAT 相近的统一 JSON

JSON 延续当前模板的信号字段，升级为 `schema_version: 3`。默认分块格式示意如下：

```json
{
  "schema_version": 3,
  "template_id": "vmc_unified_20260918_v1",
  "storage": {
    "kind": "indexed_stream_chunks",
    "version": 1,
    "layout_sha256": "..."
  },
  "timestamp": {
    "value_type": "uint64",
    "unit": "tick",
    "scale": null
  },
  "streams": [
    {
      "stream_id": 231,
      "source_message_id": "0x00E7",
      "name": "ah_nav",
      "payload_length": 139,
      "endianness": "big",
      "signals": [
        {
          "name": "cur_pos_x",
          "source_name": "cur_pos_x",
          "byte_offset": 0,
          "value_type": "float32",
          "source_type": "r32",
          "scale": 1.0,
          "group": "ah_nav[0x00E7]"
        }
      ]
    }
  ],
  "source_segments": []
}
```

与现有 JSON 的关系：

- `signals` 中的名称、偏移、类型、倍率、偏移量、单位、说明和分组规则继续沿用；
- 原来的顶层 `signals` 改为每个流自己的 `streams[].signals`，字段偏移相对本流负载；
- `storage` 指定紧凑分块或固定信封；固定信封导出仍填写 `record_size`、`framing`、`dispatch` 和 `payload_offset`；
- `timestamp` 指定每条记录的真实横轴字段；
- 增加 `uint64` / `int64` 类型，时间戳不再拆成高低两条普通曲线；
- 未知时间单位使用 `tick`，不会错误标成秒；
- 重名字段追加 `_2`、`_3`，`source_name` 保留表头原名；
- 单位、倍率和说明只有在设备资料确认后填写，表头没有的信息保持空值。

该 JSON 仍是一份用户可查看和补充说明的文本模板，没有把协议结构藏进私有数据库。

## 6. PAT 解析器改造

默认分块格式新增 `IndexedMixedReader`：

1. 打开时只读取 BIN 文件头、文件尾索引和 JSON；
2. 根据当前选择的信号和可见时间范围查找相交数据块；
3. 校验块 CRC、负载长度和结构指纹；
4. 只解码所需字段，直接以块内时间戳生成横轴；
5. 来源段变化时插入断点，防止跨不连续时间段连线；
6. 缓存按“流 + 字段 + 时间范围”管理，达到上限后淘汰不可见数据。

固定信封兼容文件由 `RoutedRecordParser` 顺序处理，同样按流 ID 只解码匹配字段。两种物理布局输出相同的多频率序列接口。

信号树在加载 JSON 后即可展示全部字段。统计值按数据块流式计算并缓存，不要求先建立全量 `QPointF`。时序图和空间图每条可见曲线仍限制绘制点数，精确导出和光标局部查询按原始块读取。

现有固定帧 `RecordParser`、串口 `SerialFrameAssembler` 和 schema 1/2 保持不变；schema 3 进入独立路由解析路径，降低回归风险。

## 7. 多文件合并规则

1. 每个输入文件独立读取全局头和描述表；
2. 每个描述项计算结构签名并映射为流 ID；
3. 同 ID 同结构归入同一流，同 ID 不同结构建立新流版本；
4. 每条记录保留来源段、源序号、原始前缀、时间戳和负载；
5. 时间基准未知时不根据文件名、修改时间或选择顺序推导 UTC；
6. 时间戳回退建立新段或标记异常，不直接覆盖旧点；
7. 损坏文件默认在首个无法确认的边界停止该段；恢复扫描必须由用户显式开启，并给恢复记录设置状态位；
8. 输出使用临时文件和 `QSaveFile` 原子提交，取消、磁盘写满或 JSON 写入失败不会覆盖已有有效结果。

## 8. 性能估算与预算

| 项目 | 当前样本 | 10 倍 | 20 倍 |
| --- | ---: | ---: | ---: |
| 有效点数 | 约 800 万 | 约 8,000 万 | 约 1.6 亿 |
| 全量 `QPointF` 原始点载荷 | 122 MiB | 1.22 GiB | 2.44 GiB |
| 179 字节固定信封 BIN | 132 MiB | 1.29 GiB | 2.59 GiB |
| 紧凑分块 BIN 估算 | 约 29–33 MiB | 约 0.3 GiB | 约 0.6 GiB |

全量 `QPointF` 只是点坐标，实际运行还包含容器余量、图表副本、统计、显示变换和派生数据，10–20 倍数据不能采用全量驻留。

默认性能预算：

- 打开文件只读取 JSON、文件头和索引，新增内存目标不超过 32 MiB；
- 解码缓存默认 128 MiB，低内存模式 64 MiB，可由用户调整；
- 转换过程读写缓冲总量不超过 64 MiB；
- 每条可见曲线最多提交约 4,000 个抽稀点，抽稀保留区间最小值和最大值；
- 统计、差/和以及二维/三维数据按块执行，结果缓存也受同一内存预算限制；
- 离线空间轨迹不再永久复制全量历史，而是保存块索引和分层概览，放大局部时读取原始块。

因此文件规模增长主要增加磁盘占用和按需读取时间，不应线性增加常驻内存。

## 9. 模块划分

| 模块 | 职责 |
| --- | --- |
| `VmcLogReader` | 流式读取描述表和源帧，验证 ID、长度、尾部及时间状态 |
| `UnifiedLogFormat` | 解析 schema 3、流路由、时间戳和来源段 |
| `UnifiedLogWriter` | 按流分块写入、维护有界缓冲、CRC、索引和原子提交；可选固定信封导出 |
| `IndexedMixedReader` | 按索引读取指定流和时间范围，不扫描无关数据 |
| `RoutedRecordParser` | 读取兼容固定信封，按流 ID 解码匹配字段 |
| `MixedDataSession` | 多频率序列、段断点、有界缓存、流式统计和分层概览 |
| `MixedLogImportDialog` | 扫描摘要、文件列表、冲突提示、转换进度和结果入口 |

核心读写模块只依赖 Qt Core；界面层依赖 Widgets。转换和扫描在工作线程执行，通过有界批次更新进度。

## 10. 实施和验收

### 阶段 A：源格式读取

- 样本必须得到 55 个描述项、775,975 帧、39 个实际普通流和 1,497 字节尾填充；
- 覆盖截断描述、未知类型、长度不符、时间回退、重名字段和异常尾部测试。

### 阶段 B：紧凑分块与 JSON

- 生成按流分块、带 CRC 和文件尾索引的统一 BIN 及 schema 3 JSON；
- 每条输出记录可追溯到来源文件及源序号；
- 逐流时间戳和有效负载与源文件逐字节一致；
- 结构冲突生成不同流，不静默覆盖。

### 阶段 C：PAT 路由解析

- 路由全量核验的有效点数为 8,006,657，而不是 `775,964 × 427`；正常打开不创建这些点；
- 各流样本数与扫描统计一致；
- `ah_nav.abz` 首值约为 `-9.75662`；
- 不匹配消息不向信号序列追加零值或无效点；
- 时序、检索、统计、差/和及二维/三维视图可使用不同流信号。

### 阶段 D：多文件与稳定性

- 验证连续段、时间戳重置、重复文件、同 ID 结构冲突、损坏和取消；
- 段间时间关系未知时曲线断开；
- 转换失败不产生可被 PAT 误打开的半成品；
- 在目标机器记录转换耗时、打开耗时、峰值内存和所选信号加载耗时。
- 使用当前样本的 10 倍和 20 倍合成输入验证常驻内存受预算限制，不随总点数线性增长。

## 11. 最终结论

用户提出的路径可行：把原始异构日志重构成一个按流分块、带索引的紧凑 BIN，再由一份与 PAT 现有信号定义相近的 JSON 进行解析。解析器只加载所需流、字段和时间窗口，并直接使用记录时间戳作为横轴。179 字节固定记录可以保留为兼容导出；默认分析格式必须使用紧凑分块和有界缓存，才能覆盖当前样本 10–20 倍的数据规模。
